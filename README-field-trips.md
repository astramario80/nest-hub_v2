## One trip record through six stages

1. **Plan.** Enter purpose, destination/address, one to five scheduled days, departure and return, transport for each day, food, materials/dress, paperwork deadline, and participants once. Participant selection uses stable roster identities, including students outside CTSO who join a particular trip. Model an actual overnight stay explicitly; multiple day trips do not imply an overnight trip.
2. **District request.** Prepare reusable trip details and attachments for Informed K12. Track draft, submitted, approved, rejected/returned, and cancelled separately from student readiness. Retain district request ID, link, approval reference, decision timestamp, and actor. Changes to dates, location, transport, or other material approved facts require a district approval recheck. The district is the source of approval.
3. **Student preparation.** Each invited student sees the itinerary, meeting point, transport, food, clothing/materials, deadlines, and that trip's blank permission form. A signed-in student can submit their own completed form. File received, under review, correction requested, and verified are distinct states. A form for another trip does not clear this one. Provide an organizer-recorded paper hand-in path.
4. **Communicate.** Choose trip information, missing-form reminder, schedule change/cancellation, or absence notice. Resolve actual recipients from verified roster and school notification roles. Preview exact recipients, purpose, text, and calendar effect before a deliberate send. Send student reminders individually. Use the same event IDs for updates and cancellations; an information reminder must not duplicate an invitation.
5. **Event day.** Each day has independent movement and roll calls at departure, arrival, and return or named additional checkpoints. Students check themselves in during an organizer-opened window. Record roll calls even if paperwork is incomplete: a physical observation is independent of travel clearance. A student's sign-out request does not release them; the supervising adult confirms departure and records the time, actor, and reason/hand-off where needed. Do not infer presence from a form or infer absence from a missing form.
6. **Reconcile and close.** Resolve unmarked students, absences, check-in discrepancies, and pending departures. Confirm everyone is accounted for, close the day, and retain the audit trail. Archive the trip without deleting records or changing document sharing. Retain original approved district documents and references.

The preview demonstrates the principal transitions with one roll-call value per trip day. Named checkpoints, guardian hand-off detail, offline reconciliation, live roster integration, actual document review, and live invitation delivery remain implementation work. The preview now includes food-arrangement selections with notes and per-trip participant selection at creation or through the Students tab. Its picker supports individual search, period/group filters, and group selection using fictional students. Participant changes flow to paperwork, attendance, reminder audiences, and the sample student view; active-day roster changes are blocked until reconciliation.

## Server and data design

Reuse NEST's HttpOnly session cookie, same-origin checks, and school-owned Apps Script bridge. New website endpoint `/api/field-trips` forwards allowlisted operations under a dedicated school action. The school service revalidates the session and role and resolves canonical student identity for each operation. Use roster-linked manual accounts only through the existing verified `memberEmail_` logic and current enrollment checks.

Proposed records:

| Record | Identity and contents |
| --- | --- |
| Trip | Stable ID, revision, organizer, title, purpose, destinations, instructions, deadlines, lifecycle |
| Trip day | Trip ID + day ID, local date, time zone, departure/return, transport, open/closed windows |
| Participant | Trip ID + verified student ID, eligibility/invitation, roster provenance, withdrawn status |
| Paperwork | Trip ID + participant + requirement + revision, received/reviewed state, private document reference |
| District request | Trip ID + approved-details revision, external request ID/link, status and decision evidence |
| Roll call | Day + checkpoint + participant, observed status, actor and timestamp |
| Movement | Append-only check-in/request/release events; derived current state |
| Communication | Trip/revision/type, recipient snapshot, template, provider IDs, invitation UIDs, delivery outcome |
| Audit | Operation ID, revision, authenticated actor, time, before/after references, outcome |

Prefer a school-owned central register for website state with explicit IDs and link it to existing trip folders/attendee workbooks. Review whether a transactional database is needed before committing attendance concurrency to Sheets. With a Sheets-backed bridge, hold a lock and make related row/audit writes atomically through Sheets batchUpdate; enforce optimistic revision checks and operation IDs. Do not silently change live legacy sheets or leave two independent sources of truth.

Migration must explicitly choose which system writes each field. Initially retain existing creation/document/calendar automation; import and map stable event IDs through a verified one-time adapter. Next move creation behind one shared service so Google Form and website call the same logic. Do not simply append a form response row and assume the installed form-submit trigger runs. Disable duplicate invitation and reminder pathways only after successful reconciliation.

### Access and document handling

- Anonymous access returns no trip, participant, or document data.
- A student receives only their authorized trips and own document/movement records. Filter on the server, not by hiding controls or downloading the whole roster.
- Mario's verified owner identities have management rights. Student executives do not inherit field-trip management. Future chaperone access needs an explicit per-trip role and scope.
- Uploads: authorize trip membership before accepting a stream; enforce file size, magic-byte/type checks, and PDF/JPG/PNG allowlists; private storage only; exact participant/trip binding; authenticated downloads with no shared folders or public file links. Use a quarantine/review flow where available. Never mark a file verified because an upload succeeded.
- Preserve original health and emergency documents with existing restricted access. Avoid copying them into the student-facing page, public assets, notifications, logs, browser storage, or fixture data.
- Event sign-out records the request separately from actual release. Neither an invitation nor a permission form is proof of presence or release. Keep organizer overrides explicit and audited.
- Idempotency: uploads, saves, check-ins, sign-outs, and sends accept stable operation IDs. Retried uncertain sends read the prior outcome rather than sending again. Prevent concurrent stale saves from overwriting attendance.
- Mobile use must tolerate stale state and failed connectivity. Show "not saved" until server confirmation; do not queue silent releases. Provide printable organizer roster and an explicit reconciliation path for offline events.

### Calendar and communications

Keep existing event calendar mapping unless the organizer chooses a change. Resolve affected teachers, office/attendance, transport, invited students, guardians, or chaperones from verified sources for each notification purpose. Add guardian messages only after the contact source and allowed audience are verified. Staff recipient defaults are not a substitute for verifying actual role assignments.

Calendar creates/updates require review of existing IDs, calendar ownership, and write scopes. Current local school bridge manifest has `calendar.readonly`; do not broaden that scope without user consent. An ICS attachment can offer an interim add-to-calendar action, but it is not proof of a calendar invitation sent or an RSVP-capable event. Never send real test messages to students, families, or staff.

## Parent, student, and organizer permission workflow

Added to the local preview on October 28, 2026. No parent email has been sent, real identity verified, or valid signature collected. The organizer has confirmed that parent electronic signatures are accepted. Actual parent identity/access verification and delivery remain integration work.

- Student supplies a parent/guardian name and matching email entries for their invited event. An arbitrary student-supplied address is an unverified contact proposal, never proof of guardianship.
- Organizer checks against an authorized district guardian/contact record or a documented direct confirmation before preparing an invitation. Actual guardian-directory access is not implemented. The preview uses an explicitly labeled sample checkbox.
- Production invitation goes to the checked contact and opens only the named child's trip. Require verification of email access and guardian binding; a forwarded link alone must not open the form. Use opaque expiring, revocable tokens without child/contact data in URLs, hashed token storage, replay protection, and scoped server sessions.
- Keep parent identity separate from district-student account registration. Parent access must not grant a NEST student, roster, staff, or general management session. Existing NEST registration is district-address restricted and should remain so.
- Parent reviews the exact generated district document plus itinerary, supplies the district-required parent/contact fields, and grants or declines permission. Email control alone cannot establish legal authority. Preserve required district acknowledgments and approved signature capture.
- Signature completion creates a PDF using the original per-event district PDF page as its base, fills the existing spaces, and appends itinerary/signing evidence separately. Do not redraw, reword, resize, or rearrange the district form. Preserve the form's original header, text, lines, and coordinates. The prototype captures a finger, stylus, or mouse drawing in a large modal, then embeds the resulting transparent image in the original PDF signature space. Typed parent names identify the signer but are not used as the signature.
- Parent and organizer can download the full PDF. The student sees progress and shared trip updates, without the parent-completed medical, emergency-contact, or address fields. These parent-private fields must be removed from server responses to students, not just hidden in the browser.
- Parent signature yields "awaiting organizer review". It does not automatically verify paperwork or establish attendance. Declining permission produces no consent PDF. A later material trip change invalidates the prior signature for current clearance and requires a new document/signature, while preserving the historical original.
- Shared Family updates let the student, checked parent, and organizer exchange trip questions. The shared channel must explicitly exclude parent-private health/contact fields. Production notifications require separately verified recipients and actual delivery evidence.
- Store final originals in private school-controlled event storage. The website is an authorized access window, not a public folder. Preserve immutable original PDF bytes, template version/hash, signed content/version, verified identity and guardian binding, consent evidence, server timestamps, document hash, and access/revocation history according to district policy. Downloads and emailing require independent recipient authorization. Retention and any additional audit attributes need district decisions.

### Drawn signatures and incomplete parent contacts

The signature line opens a large native dialog with the background inert and page scrolling locked. Canvas touch handling prevents drawing gestures from scrolling the page. Undo, Clear, Cancel, and Use this signature are explicit. Escape cancels edits. Closing the editor does not submit permission. A blank tap cannot satisfy the drawn-signature check. Existing strokes are cloned during edits, so cancellation preserves the committed image. Original canvas coordinates and uniform scaling preserve signature proportions through resizing or rotation; the cropped image fits the original signature-line box without changing district text.

No parent email means the contact remains incomplete and permission remains pending. The signed-paper alternative remains available. Requests, delivery results, contact changes, parent access, signing, declines, and review decisions should be recorded as evidence of the process; neither absence of an email nor a student's assertion is treated as completed parental permission. This describes application behavior, not a determination of legal responsibility.

All example signature artwork is fictional and labeled SAMPLE. The live system must perform its own parent-access authorization, validate the submitted signature payload, bind it to the current document, and generate/store the PDF on the server. The local editor's mode selector and client-side stroke validation are not production security controls.
