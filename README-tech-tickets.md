# NEST Tech Tickets

`/tech-tickets` replaces the Google Form entry in Help & Support. Signed-in current students report issues and see tickets they created. `/tech-management` is the Software Technician workspace; current roster members hired as Software Technician and website administrators can view all tickets, assign current technicians, change statuses, reopen tickets, and add reporter-visible or internal updates. Permission checks run in the school bridge on every request. The shared menu includes Leadership → Software Techs.

The shared `js/main.js` loads `js/tech-report.js` and its stylesheet on NEST pages. The floating Report a bug button supports pointer dragging, arrow-key movement, and a persistent browser-local position. It captures the visible page before opening the form, using a self-hosted MIT-licensed html2canvas 1.4.1. Capture is an approximate DOM rendering, not an OS screenshot: cross-origin embeds and video can be omitted. Inputs, textareas, editable content, and explicit `[data-private]` elements are excluded. Screenshots may be reviewed, removed, or replaced before submission. Submitted context contains the pathname only, never URL query parameters or fragments.

`api/tech-tickets.mjs` checks the NEST HttpOnly session and same-origin writes, then calls `auth-tech-tickets` in `google-spinner/TechTickets.js`. Ticket data is stored as RAW JSON cells in a dedicated NEST Tech Tickets tab of the existing tech workbook. New ticket IDs and update action IDs make exact retries idempotent; hashes prevent stale overwrites. Reporter identity and timestamps come from the server. A reporter sees only their own tickets and public updates; private image file IDs and submission hashes are never returned. Screenshot files are created in a private, app-created Google Drive folder and read through an authenticated API operation with current ticket access checks. Screenshots remain private. Emails occur only through the explicit escalation actions described below.

The technician dashboard groups tickets by school year (August 1 boundary, America/Los_Angeles), and filters active versus resolved/closed records. Open tickets remain accessible after year rollover through the year selector. The top room-health overview combines the dials, issue-type chart, device and status tables. Each graphic has its own Export to leader’s slide control, using the selected school year and an authorized destination division. The original Google Form workbook remains unchanged; only its TechTickets response tab is exposed through the read-only earlier-ticket history view. Builder and barometer/helper tabs are excluded; those legacy rows have not been migrated into editable native tickets or their new statistics.

Signed-in technicians receive in-site banners on any shared-script NEST page. Checks run every 30 seconds while the tab is visible, plus when it becomes visible. The first visit establishes a baseline; subsequent visits use a per-account browser cursor. Alerts are not push notifications and cannot run when browsers are closed, suspended, or offline. Ticket pages refresh every 60 seconds while visible and no detail dialog is open, preserving update drafts.

Limits: 12 submissions per account per hour; JPEG screenshot data URLs under 500,000 characters; 10,000 native tickets per workbook tab; up to 100 history entries per ticket and a 45,000-character serialized ticket limit. Legacy history is bounded to 10,000 data rows per sheet. Test coverage includes reporter isolation, role and roster revocation, private notes, screenshot authorization, stale writes, idempotent retries, school-year boundaries, dashboard export totals, and uncertain-submit drafts.

Release evidence and the exact production source baseline are retained under ignored `tmp/tech-tickets/`. The school manifest and unrelated modules are preserved. Website publication is assembled from the actual current production deployment rather than publishing unrelated working-directory changes.

## Owner-controlled escalation

Software Technicians can escalate a saved ticket to Mario, creating a review queue entry and a notification to mpenalver@bethelsd.org. Only Mario’s three explicitly configured, verified NEST identities can load the recipient directory, preview an outside escalation, send it, or reconcile an uncertain email result. General website administrator status does not grant outside sending rights. The original workbook sender also receives an explicit Mario-only guard so the older spreadsheet workflow cannot give student technicians recipient-selection rights.

`google-spinner/TechEscalation.js` reads recipient names, positions and email addresses live from NEST Database → Notifications!H2:J1000. A missing name falls back to the position and email. Software Request and CTE-specific need recommend the CTE TOSA row; other types recommend Tech Support. Mario may choose another listed recipient. The preview binds the stored ticket version, current recipient row, subject, message and attachment presence; directory or message changes require a new preview.

The existing sendTechTicketEmails template is preserved: summary as subject, reporter/division, station and Bethel barcode table, description, attachment reference and NEST Software Tech Team signature. Station barcodes resolve against the original LaptopInventory!E2:E1000 when possible, otherwise “Not provided” is explicit. Private technician notes are excluded. New screenshots travel as JPEG email attachments without changing Drive sharing. After a confirmed outside send the ticket status is Pending.

Each send records an intent before MailApp is called. Exact action retries return the saved outcome without sending again. A timeout or uncertain delivery blocks further emails until Mario checks sent mail and explicitly records sent or not sent. Saving a normal ticket update or setting a status never sends an outside email. The owner-review queue has its own management filter and in-site banners for Mario.

## Room tech health

Both ticket landing pages show room-wide aggregate charts for the selected school year, followed by the user's existing ticket list. A student's individual records remain limited to their own reports. The school bridge returns only numerical aggregates and issue-type labels in `roomHealth`; no other reporter's identity, ticket ID, description, notes, screenshot, or station text is included.

The Open tickets dial divides active tickets by all website tickets in that year. The Open 7+ days dial divides open tickets at least seven elapsed days old by all open tickets. Both dials use green through 25%, amber through 50%, and red above 50%, with count/denominator text and accessible labels. Empty denominators show a neutral dash. Stacked bars compare issue types, separating open from resolved/closed tickets. Additional measures count unique normalized station/device labels with active reports, unassigned open tickets, and the age of the oldest open report. These statistics use the native website tickets; earlier Google Form history remains a separate read-only archive. Search and status filters affect the list; year selection also changes the room overview.

The floating Report a bug control is 32px high on pointer devices, uses 11px text and partial opacity, and becomes solid on hover, keyboard focus, or active interaction. Touch targets remain at least 36px high. Dragging, keyboard repositioning and browser-local position persistence are unchanged.

## Embedded landing-page intake

The Tech Tickets landing page mounts the shared ticket form directly below its introduction rather than using a report button to open a modal. The editor stays hidden until NEST sign-in and an authenticated catalog read succeed. Opening the landing page while signed out prompts for sign-in before fields are available. There is no separate Sign In to NEST button within the form. Screenshot uploads and exact submission retries remain available. Its My tickets link jumps to the dashboard below. On this page the floating reporter captures as requested and scrolls to the same inline form; other pages continue using the popup. This presentation change requires no backend or escalation changes.


## Room machines, targets, and recovery (2026-11-12)

Inventory & Purchasing → Equipment → Room machines is the shared machine editor. Existing Inventory Director and website administrator checks apply to every read and write. Add/edit accepts a name, manufacturer serial number, machine type, optional filament pricing profile, and PNG/JPEG/WebP icon upload. The browser resizes the icon to 128×128 WebP, at most 20,000 data-URL characters. The server validates file signatures and rejects SVG and external URLs. Icons are saved with the machine, so no public Drive uploads or new image permissions are required.

`google-spinner/RoomMachines.js` owns the catalog in hardware workbook `1dRyHDG8UbdjaOyQVXaGWS6UoqiEJr5uOg2LUQPM_rEY`, **Room Machines** columns A:B (stable ID and RAW JSON). Until overridden, it derives registered printers from **3d Printers** A:D and supplies Laser CNC/Wazer CNC placeholders with empty serials. No serial numbers are invented. An edit saves an override; removal archives the machine and suppresses its seeded choice. Catalog writes and InventoryWebLog audit records commit together under the existing inventory lock. Existing ticket and queue records retain their original details.

Machine types `3d-printer`, `laser-cnc`, and `waterjet-cnc` appear in fabrication; `other` appears only in tech reports. The authenticated fabrication access response supplies the same machine ID, name, icon, type and version. The form renders icon cards. Printers need an explicit supported filament profile (Sketch Large, Replicator +, Method); unconfigured printers show a setup message and cannot be requested. Fabrication submission validates the current active machine and version, recomputes pricing for its profile, and saves the readable machine name in the existing queue. Exact already-saved submissions remain replayable after inventory changes.

Computer / hardware reports display checkbox station choices from LaptopInventory B:C, without the sheet's student emails. Hardware / machines displays all active room machines. Both support one or multiple selections and Select all / Deselect all. The school server validates selected IDs and saves name/serial snapshots for later reporting and escalation. Room-health affected-equipment counts use each target rather than the combined label.

For uncertain ticket saves, the bridge may replay only the same immutable create request, whose UUID and fingerprint deduplicate on the school server. Email escalation and other mutations retain their existing no-replay rules. If creation still loses its response, the API performs a separate authenticated lookup for that reporter's exact submission ID before reporting uncertainty. Inventory view, purchasing shell view and fabrication access also use bounded read retries. Drafts remain frozen for an exact retry when confirmation is unavailable. This is recovery behavior, not proof that every future school outage will succeed.

## Role-based landing order

`canViewOverview` is computed from current hired roles plus current division membership. Software Technicians, Division Managers, Assistant Managers, CEO, Executive Vice-President, CFO, Operations Officers, and website administrators get room health and their ticket list before the embedded form. This presentation flag does not grant management, other reporters' private ticket access, or outside-email escalation. Current Software Technicians and website administrators retain the separate management workspace; only Mario retains outside sending rights.

## Direct graphic exports and consolidated overview

`TechSlides.js` computes sanitized, room-wide snapshots for open share, open 7+ days, issue types, device counts, status counts and room indicators. Current Software Technicians, managers/assistants and executive leadership may export only to their authorized division destinations; administrators and current cross-division executives may select all configured divisions. Private issue titles, descriptions, reporters, notes and screenshots are excluded from exported graphics. Device-count tables count each selected device independently. Large device tables export the 12 most-reported devices plus an explicit Other row; all totals are retained.

`api/tech-slide-export.mjs` accepts only graphic kind, year, destination period and a retry UUID. It obtains an authorized server snapshot, renders a 1600×900 PNG with bundled OFL Montserrat fonts, and sends it through a second permission/version check. Browser-supplied images, deck IDs and statistics are rejected. `google-control-center/TechGraphicExport.js` rechecks live roles and resolves only the division’s existing Software Technician individual deck inside Division Leader Slides. Each explicit export appends a new blank slide containing a regular image with margins. The leader may move, resize or remove the image. Existing slides, images, text, notes and sharing stay intact. Manager decks are never export destinations; there is no deck rebuild or email.

Export action IDs bind the actor, division, graphic and year. Exact uncertain retries return the saved result or recover the marked image; they do not append duplicates. A new explicit export adds another slide. Existing deck sharing governs who can open the returned link. Graphics are dated snapshots, not live linked Google charts. The new-slide workflow uses its own V3 request namespace so older two-deck or existing-slide results cannot replay as a new-slide success.

The Earlier Google Form tickets operation allowlists only `TechTickets`. It never fetches Builder, TechTicketsBarometer, TechTicketBarometer, or newly added helper tabs. The standalone Leadership meeting tables/copy-button/CSV section was removed; its aggregate tables now live next to the dials, each with its own export control.
